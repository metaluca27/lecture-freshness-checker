# Liner API 동작 시험 기록

시험일 2026-11-12. 키는 Windows 사용자 환경변수 `LINER_API_KEY`에서 읽었고, 이 문서와 저장소에는 키 값을 적지 않는다.

## 결과 요약

| 시험 | 결과 | 한 줄 정리 |
|---|---|---|
| Search | 통과 | 설계대로 `results[].url/title/description/date`가 온다 |
| Model 글자 JSON 답변 | 통과 | `json_schema` 방식으로 받는다. `json_object`는 쓰지 않는다 |
| Model 그림 읽기 | 통과 | 앱 화면 3장의 메뉴와 버튼 이름을 맞게 읽었다 |
| 공식 문서 본문 읽기 | 통과 | 평범한 `fetch`로 본문이 나온다. 문서 주소 뒤에 `.md`를 붙이면 더 깨끗하다 |

네 가지 모두 통과라 계획의 대안(다른 비전 모델, 시연 자료 교체)은 쓰지 않는다.

## 1. Search

- 주소: `POST https://platform.liner.com/api/v1/tools/search/web`
- 인증: `x-api-key` 헤더
- 요청: `{ "query": "...", "max_results": 5 }`
- 응답: `{ requestId, results: [{ title, url, hostname, faviconUrl, description, date }], totalCount }`
- `date`는 `null`일 수 있다(공식 사이트 결과 2건 모두 `null`).
- `hostname`이 따로 와서 출처 등급을 매길 때 바로 쓸 수 있다.
- 응답에 비용 값은 없다.
- 질문 "Antigravity 요금제 가격" 결과 5건: `antigravity.google` 2건(요금 페이지 영문, 한글), 그 외 안내 사이트 2건, 레딧 1건. 비공식 출처가 섞여 나오므로 출처 등급 구분이 꼭 필요하다.

## 2. Model 글자 답변

- 주소: `POST https://platform.liner.com/api/v1/chat/completions` (OpenAI 형식)
- 인증: `Authorization: Bearer <키>`
- 모델: `liner-mark-1.3`
- 출력 길이 제한은 `max_completion_tokens`를 쓴다. `max_tokens`를 보내면 400으로 거절된다.
- JSON 답변 방식 세 가지를 같은 한글 슬라이드 문장으로 시험했다.

| 방식 | 결과 |
|---|---|
| 지시문만으로 JSON 요청 | 200. 올바른 JSON이 왔지만 형식 보장은 없다 |
| `response_format: { type: "json_object" }` | 영어 한 줄 질문은 200, 한글 system+user 구성은 400. 원인을 못 밝혔으므로 쓰지 않는다 |
| `response_format: { type: "json_schema", strict: true }` | 200. 스키마대로 왔다. **이 방식을 쓴다** |

- 시험 문장에서 요금(19.99달러), 개수(60개), 메뉴 이름(Agent Manager) 세 가지를 뽑았고, 일반 설명("구글이 만든 AI 코딩 도구")은 뺐다. 설계의 골라내기 의도와 맞는다.
- 응답 시간 3~5초, 토큰 약 180 입력 / 100 출력.
- 오류 응답 형식: `{ "error": { "message", "type", "param", "code" } }`. 400의 `message`가 원인을 알려 주지 않으므로, 요청 형식은 이 문서에 적힌 것만 쓴다.

## 3. Model 그림 읽기

- 같은 주소, 같은 모델. `content`에 `{ "type": "image_url", "image_url": { "url": "data:image/png;base64,..." } }`를 넣는다.
- 외부 그림 주소는 못 쓰고 base64 데이터 주소만 된다(문서 기준). 요청당 최대 10장.
- 시험 그림은 안티그라비티 강의 PPT에 쓴 앱 화면 3장(개인정보가 없는 화면만 골랐다).

| 그림 | 모델이 읽은 것 | 눈으로 확인 |
|---|---|---|
| 왼쪽 메뉴 | New Conversation, Automations, Customizations | 일치 |
| 마켓플레이스 위쪽 | Customizations, Marketplace, Installed, + Add, Details | 일치 |
| 마켓플레이스 구글 묶음 | Marketplace, Installed, Gemini API, Chrome DevTools, Android CLI, Firebase, Science, Google Antigravity SDK, + See 6 more | 원본과 대조는 아직 안 함 |

- 그림 1장당 입력 약 1,100토큰, 응답 4~7초.

## 4. 공식 문서 본문 읽기

워커가 하듯 평범한 `fetch`로 가져와 태그를 걷어 냈다.

| 주소 | 결과 |
|---|---|
| `antigravity.google/docs` | 200이지만 본문은 "Redirecting to: /docs/getting-started" 한 줄. HTML 안내 방식의 이동이라 `fetch`가 따라가지 않는다 |
| `antigravity.google/docs/getting-started` | 본문 약 21,600자 |
| `antigravity.google/docs/getting-started.md` | Markdown 약 20,900자. 메뉴 글자가 섞이지 않아 가장 깨끗하다 |
| `antigravity.google/docs/changelog` | 본문 약 524,000자. 통째로 모델에 넣기에는 너무 길다 |
| `antigravity.google/pricing` | 본문 약 4,300자. "$0/month", "$30 USD per seat per month" 같은 가격 글자가 보인다 |
| `antigravity.google/llms.txt` | 문서 주소 124개 목록 |

구현에 반영할 것:

1. "Redirecting to:" 본문이 오면 그 주소로 한 번 더 가져온다.
2. `/docs/...` 주소는 `.md`를 먼저 시도하고, 안 되면 HTML로 읽는다.
3. 긴 본문은 통째로 넣지 않고, 슬라이드 내용의 핵심 낱말이 있는 주변만 잘라 모델에 준다.
4. 근거 대조는 잘라 낸 조각이 아니라 가져온 본문 전체를 상대로 한다.

## 5. 비용

- 응답에 `usage.cost` 값은 없다. `usage.prompt_tokens`, `usage.completion_tokens`만 온다. 비용은 토큰 수에 단가를 곱해 직접 계산하고, 실제 차감은 Liner Platform 대시보드에서 확인한다.
- 단가(Liner 가격 문서, 2026-11-12 확인): `liner-mark-1.3` 입력 100만 토큰당 $1.00, 출력 $5.00. Search는 호출당 $0.001(Premium Data 포함 시 $0.002). Deep Research Agent는 호출당 $0.20.
- 계산값: 글자 판정 1회 약 $0.001, 그림 1장 약 $0.002, 검색 1회 $0.001~0.002.
- 오늘 시험 전체 호출은 Model 13회(그중 3회는 400 거절), Search 1회로, 계산상 $0.02 미만이다. 대시보드의 실제 차감액과는 아직 맞춰 보지 않았다.

## 6. 계획과 달라진 점

| 계획 | 실제 | 조치 |
|---|---|---|
| 비용은 응답의 `usage.cost`를 기록 | 그 값이 없다 | 토큰 수로 계산한다 |
| JSON 답변 방식 미정 | `json_schema`만 안정적 | `chatJson`은 스키마를 받아 `json_schema`로 요청한다 |
| 본문은 HTML에서 꺼낸다 | `.md` 주소가 더 깨끗하고, `/docs`는 안내 방식으로 이동한다 | `fetchPageText`에 위 1~3번을 넣는다 |

## 9. PDF 지원과 가상 자료 측정 (2026-11-15)

- PDF: 글자가 있는 PDF(한글에서 저장한 10쪽)는 0.3초에 읽혔고, 그림으로만 된 PDF(20쪽)는 쪽을 그림으로 만들어 읽는 데 2초가 걸렸다. 그림 PDF 20쪽 전체 검사는 1분 26초, 내용 53개.
- 가상 사내 교육자료 측정 결과와 주의할 점은 `docs/extension-case.md` 에 적었다. 요약: 세 번 실행에서 27번 중 26번 정답, 심어 둔 낡은 정보 12번 중 12번, 억울한 바뀜 0번.
- 이 측정으로 고친 것: 공식 사이트를 여러 곳 지정하면 첫 번째만 검색하던 문제. 이제 `(site:a OR site:b) 검색어` 로 한 번에 묶어 찾는다.
- 공식 도메인 아래의 사용자 게시판 글(`support.google.com/…/thread/…`)은 공식 문서가 아니므로 3등급으로 내리고 열지 않는다.
- 안티그라비티 앱 최신 버전이 11-13에 v2.32.0 으로 올라갔다(11-12 시험 때는 v2.31.2). 측정 수치는 날짜와 함께 봐야 한다.

## 10. 확인 못 함 줄이기와 "그대로" 조이기 (2026-11-15)

실제 강의 PPT(15장, 그림으로만 된 자료)를 배포된 화면에서 돌리니 41개 중 32개가 확인 못 함이었다. 원인을 나눠 고쳤다.

| 고친 것 | 내용 |
|---|---|
| 재검색 | 근거를 못 찾으면 본문에 나올 법한 낱말로 한 번 더 검색해, 아직 읽지 않은 공식 페이지를 본다 |
| 공식 블로그 | 사이트 제안에 공식 고객센터와 공식 블로그를 넣게 했다. 이름 변경이나 새 기능 발표는 블로그에 실린다 |
| 덜 뽑기 | 화면 생김새를 풀어 쓴 말, 뭉뚱그린 사용 순서, 우리말로 옮긴 메뉴 이름은 뽑지 않는다 |
| 숫자 대조 | "그대로"는 슬라이드 문장의 숫자가 근거 문장에 모두 있을 때만 인정한다. 코드로 확인한다 |
| 판정 규칙 | 본문이 더 자세할 뿐이면 바뀜이 아니다. 세어서 얻은 숫자는 근거가 아니다. 일치·불일치 문장이 둘 다 있으면 둘 다 적는다 |

같은 PPT, 공식 사이트 notebook.google.com(1등급), support.google.com·blog.google(2등급):

| | 고치기 전 | 재검색·블로그·덜 뽑기 | 숫자 대조까지 |
|---|---|---|---|
| 뽑힌 내용 | 41 | 29 | 31 |
| 바뀜 | 2(둘 다 억울한 판정) | 2(둘 다 억울한 판정) | 0 |
| 그대로 | 7 | 22 | 18 |
| 확인 못 함 | 32 | 5 | 13 |

- 가운데 열의 "그대로 22개"를 하나씩 보니, 요금 숫자가 근거 문장에 없는데 통과한 것이 있었다. 그래서 숫자 대조를 넣었고 확인 못 함이 5에서 13으로 다시 늘었다. 줄어든 숫자보다 믿을 수 있는 "그대로"가 중요하다고 판단했다.
- 한 번씩 돌린 값이다. 뽑히는 내용 수와 판정은 실행마다 조금씩 달라진다.

가상 사내 자료(세 번 실행): 27번 중 24번 일치, 심어 둔 낡은 정보 12번 중 12번, 억울한 바뀜 0번, 공식 문서에 없는 내용을 단정한 것 0번. 어긋난 3번은 맞는 내용을 한 번 확인 못 함으로 본 것과, 덜 뽑게 한 탓에 "월 0달러"가 두 번 뽑히지 않은 것이다.

## 11. 문서 제목을 메뉴 이름으로 잘못 본 오판 (2026-11-18)

- 실제 강의 PPT 28장을 배포된 검사기로 돌리니 "바뀜"이 1개 나왔는데 오판이었다. 자료의 메뉴 이름 "Tool Permissions"를 공식 문서 페이지의 제목 "# Agent permissions"로 고치라고 했다. 문서 제목은 앱의 메뉴 이름이 아니다.
- 고친 것: 내용의 종류가 메뉴이고 바뀜의 근거가 제목 한 줄뿐이면 코드가 확인 못 함으로 돌린다(`worker/verdict.js`). 버전처럼 다른 종류는 제목 줄도 근거로 인정한다(변경 기록의 버전 제목이 그렇다).
- 같은 내용을 세 번 다시 판정해 세 번 모두 확인 못 함이 나왔다.
- 같은 실행에서 발표 노트의 "지금 최신은 2.31.0"은 뽑히지 않았다. 어떤 문장이 뽑히는지도 실행마다 다르다.
- 가상 자료 측정을 여섯 번 더 했다. 결과는 `docs/extension-case.md`의 "그 뒤에 다시 잰 결과"에 적었다.

## 12. 실행마다 결과가 다른 문제 (2026-11-18)

같은 강의 PPT 28장을 배포된 화면에서 두 번 올렸더니 한 번은 바뀜 4, 한 번은 바뀜 0이 나왔다.

- **답을 고정하는 설정은 통하지 않았다.** 같은 추출 요청을 네 번씩 보내 비교했다. 기본, `temperature: 0`, `temperature: 0` + `seed`, `reasoning_effort: "low"` 네 경우 모두 답이 서너 가지로 갈렸다. Liner 문서에 이 값들이 "반영되지 않을 수 있다"고 적힌 대로다.
- **바뀜 4개 가운데 확인한 2개는 믿기 어려웠다.** 하나는 2등급에 들어간 `codelabs.developers.google.com`의 다른 제품 예제 코드 문장("파일 크기를 10MB로 제한")을 근거로 삼은 오판이었고, 하나는 조건이 붙은 문장이었다.
- 고친 것 1: 여러 제품의 글이 모인 사이트(codelabs, 앱 장터, 저장소, 커뮤니티 등)는 공식 사이트로 제안하지 않는다. 사용자가 직접 적는 것은 막지 않는다.
- 고친 것 2: 공식 사이트만 고쳐 다시 검사할 때는 앞에서 뽑은 내용을 그대로 다시 검사한다. 무엇이 달라졌는지 비교할 수 있고 호출도 줄어든다.
- 고친 것 3(버그): 주제 파악용으로 자료 앞부분 300자를 함께 보내던 것을 표지 글자만 보내도록 바꿨다. 2장짜리 자료에서 내용이 하나도 뽑히지 않는 것을 화면 시험에서 발견했다. 모델이 해당 장의 문장을 "이미 나온 내용"으로 본 것이다. "여러 장에 되풀이되면 새로 나온 것만 뽑는다"는 지시문도 뺐다.
- 고치지 못한 것: 자료를 새로 올릴 때마다 뽑히는 문장과 판정이 달라지는 것. 모델의 답이 고정되지 않는 한 남는다.

## 13. 공식 사이트가 자동 읽기를 막은 일 (2026-11-18 ~ 11-20)

- 11-18 밤, 배포된 워커(클라우드플레어)에서 `support.google.com` 문서를 읽으면 `302`로 구글의 로봇 확인 화면(`/sorry`, 429)에 보내졌다. 같은 문서가 같은 날 낮의 측정 때는 워커에서 읽혔고, 내 PC에서는 계속 읽혔다. `antigravity.google`은 영향이 없었다.
- 그 사이 가상 자료를 돌리면 고객센터 문서가 근거인 내용(노트북 한도)이 `확인 못 함`으로 나왔다. 데모 영상은 이때 찍어서, 심어 둔 낡은 정보 4개 가운데 3개만 `바뀜`으로 나온다.
- 로봇 확인은 우회하지 않는다. 대신 읽기 실패가 `429`나 `403`이면 사유를 `page_blocked`로 따로 알리고, 읽으려던 공식 문서 주소를 결과에 담아 화면과 보고서에 "직접 열어 볼 공식 문서"로 보여 준다(`worker/check.js`, `worker/verdict.js`).
- 11-20에 배포된 워커로 가상 자료를 한 번 다시 돌렸을 때는 고객센터 문서가 읽혔고 4개가 모두 `바뀜`으로 나왔다(한 번 돌린 결과다). 언제 다시 막힐지는 알 수 없다.
